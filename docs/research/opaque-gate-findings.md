# OPAQUE feasibility gate findings and dependency approval

## Final decision — 2026-11-13

The maintainer explicitly approved `github.com/bytemare/opaque v0.18.0` for the Go backend and the exact tested `@serenity-kit/opaque@1.1.0` browser artifact, following the [documented risk acceptances](opaque-accepted-risks.md). This authorizes dependency selection and administrator-bootstrap implementation, not shipping unfinished authentication.

The approved tested Go baseline is Go 1.26.11 with `golang.org/x/crypto v0.59.0` and `golang.org/x/sys v0.50.0`; the complete tested graph and checksums remain in [the archived experiment](https://github.com/eslym/deploy-manager/tree/a069572/experiments/opaque-gate). The browser artifact identity and profile are recorded below. Future upgrades require fresh checks, not automatic extension of this approval.

The frontend memory-leak upgrade obligation is tracked in [#25](https://github.com/eslym/deploy-manager/issues/25). Exact WASM dependency/license closure and artifact-specific timing-advisory applicability remain unknown; uncertainty is accepted, not proven safe. Applicable license and notice obligations must be addressed before distribution under [#26](https://github.com/eslym/deploy-manager/issues/26); [license findings](dependency-license-compatibility.md) are not a complete browser license approval.

At the maintainer's request, both experiment directories and their runtime dependencies were removed after documenting their findings. The code, manifests, pins and verification scripts remain in Git history at the archive link above; reproduction commands below are **historical**, not commands available in the current checkout. This note preserves observed results, limitations and measurements. Initial NO-GO decisions below are superseded by this explicit approval and scoped risk acceptance, not by additional test evidence.

This standalone module is not imported by the application and does not approve its dependencies. Evidence below is conditional feasibility evidence only. No application auth, bootstrap, session, recovery, or persistent-key behavior is implemented here.

## Historical reproduction and environment

Environment measured: Ubuntu 26.04 x86-64, 4 vCPUs on Intel Pentium Silver J5005 @ 1.50GHz, host reports 7.1 GiB RAM; Go 1.26.8, Bun 1.4.4, Playwright 1.65.0, Chromium 158.0.8127.18 (headless). The Go dependency graph and Serenity package are pinned in `go.mod`/`go.sum` and `package.json`/`bun.lock`; use Bun, not npm:

```sh
go mod download
bun install --frozen-lockfile
go test ./...
bun run audit-artifact        # Fetch and verify registry tarball/provenance claims
bun run test                 # Direct Bun artifact load + HTTP interoperability
bun run test-browser-gate     # Verify failed audit prevents browser startup
bun run browser              # Audits artifact, runs Bun checks, then Chromium
bun run test-vectors          # Download pinned Go source and run its RFC vectors
```

`bun run browser` (or `bash run-browser.sh`) runs `audit-artifact` and the fast Bun protocol suite before attempting browser setup or starting Chromium; either failure stops the process. The shell wrapper may need Chromium's Ubuntu shared libraries. It unpacks required Ubuntu packages under `/tmp/opencode/opaque-gate-browser-libs` without installing system packages. It requires Bash, Bun, Playwright, and on the measured Ubuntu setup, `ldd`, `apt-get`, and `dpkg-deb`, plus network access for fetching missing packages. Package names and library paths are Ubuntu/x86-64-specific; portability to other distributions/platforms is not claimed. The tests build the isolated Go server into `/tmp/opencode/opaque-gate-server` and bind only to loopback port 4179.

`bun run test-vectors` invokes `run-rfc-vectors.py`, which explicitly runs `go mod download -json github.com/bytemare/opaque@v0.18.0`, validates the returned module path/version and uses its returned `Dir` as the working directory for `go test ./...`. It does not assume a GOPATH module-cache layout or that the source was extracted by a prior command. In that pinned source, `tests/TestOpaqueVectors` loads the shipped `tests/vectors.json`; source: [Bytemare v0.18.0 vectors_test.go](https://github.com/bytemare/opaque/blob/v0.18.0/tests/vectors_test.go) and [vectors.json](https://github.com/bytemare/opaque/blob/v0.18.0/tests/vectors.json). This runs the upstream vector suite, not a separately authored vector runner.

## What the harness proves

`server.go` is a minimal actual Bytemare v0.18.0 Go HTTP endpoint. `bun-test.mjs` loads and executes the pinned npm artifact directly in Bun; `browser-test.mjs` imports that same artifact in actual Chromium. Both exercise browser-style registration request → Go registration response → browser registration record → Go storage, then KE1 → Go KE2 → browser KE3 → Go `LoginFinish`. The browser run verified the final KE3 and confirms the client generated a session key; server acceptance of the KE3 MAC demonstrates matching AKE key derivation without transmitting either session key. It does not compare/return raw key material.

The harness retains pending login MACs in an in-memory map without expiry or a cardinality limit. It is strictly a loopback-only, short-lived feasibility harness, not a deployable server: never expose it to an untrusted network or reuse this pending-state handling in application authentication. Before any such reuse, add bounded, expiring, one-use handshake state and tests.

In the direct Bun run, registration and correct-password login complete; wrong password fails client envelope recovery; malformed (`AA`) and empty/truncated KE1 receive HTTP 400; a one-bit-modified KE3 receives HTTP 400. The real-browser run is intentionally narrower: one complete registration and one KE3-verified login, plus resource sampling. HTTP-body inspection in both paths found only protocol `value` and transaction `tx` fields, no password, serialized Serenity client state, client export key, or session key. The harness server does not log request bodies. This is a narrow protocol test, not a production-grade input-limiting/session/DoS or lifecycle review.

### Agreed interoperability profile observed

- RFC 9807 OPAQUE-3DH; Ristretto255 OPRF with SHA-512 and Ristretto255 3DH group, HKDF-SHA-512, HMAC-SHA-512, SHA-512. Go uses `opaque.DefaultConfiguration()`; Serenity 1.1.0's default package is its Ristretto build.
- Argon2id, version 0x13, explicitly configured as `iterations=1`, `memory=65536 KiB (64 MiB)`, `parallelism=4`; Serenity's custom KSF option, not the RFC's 2 GiB illustrative setting. The package uses a 16-byte all-zero salt and OPRF-output stretching. This is a tested candidate tradeoff, not an approved production policy.
- Empty OPAQUE context on both implementations (`nil`/no custom context). No custom client or server identity strings; both use the protocol's default public-key identities. The harness-only server credential lookup label is UTF-8 `gate-user` and is not an OPAQUE identity sent by the browser.
- Serenity serializes messages as URL-safe base64 without padding; Go decodes/encodes raw URL base64 around Bytemare's RFC message bytes. HTTP is local loopback JSON `{value: ...}`; login finish also carries a random transaction handle. Password and serialized client state remain in browser memory.

## Browser measurements (one headless run)

Chromium 158.0.8127.18 reported in the minimal run: package/WASM initialization **36.8 ms**; client registration start **6.2 ms**; Go registration exchange **4.1 ms**; registration finish/KSF **242.0 ms**; client login start **2.4 ms**; Go/HTTP KE2 exchange **4.2 ms**; client login finish/KSF **161.4 ms**; login start through client KE3 generation **168.0 ms**; post-test JS heap **10,000,000 bytes**. Chromium headless process-group RSS summed across six `chrome-headless-shell` processes was **437,036 KiB** after startup and **510,144 KiB** after the protocol test. RSS is a process snapshot, not peak RSS or a device-independent benchmark; the configured KSF alone requires a 64 MiB working set. No mobile-browser result is claimed. Timings vary by hardware/load and one sample is not a security calibration.

This is time-sensitive scan evidence, not a cryptographic audit.

## Decision

The maintainer has explicitly [accepted the unaudited Bytemare v0.18.0 implementation risk](opaque-accepted-risks.md#unaudited-bytemare-opaque-implementation). This resolves that specific human risk-acceptance requirement, not overall dependency approval; historical statements below must be read with this update.

Update: the maintainer has also [accepted the missing published-WASM build-records risk and consequent artifact-specific advisory uncertainty](opaque-accepted-risks.md#published-browser-wasm-build-input-uncertainty) for the exact pinned frontend candidate. These unknowns remain unknown; no upstream contact is authorized. License obligations, unaudited Bytemare risk and overall dependency approval are not waived. The NO-GO below is historical and superseded by the separate dependency approval recorded above; that approval does not establish security or license closure.

The maintainer has [accepted the frontend malformed-argument WASM memory-leak risk](opaque-accepted-risks.md), with an upgrade required as soon as the upstream fix is published. This limited acceptance does not waive any other security or license obligation.

**NO-GO for production dependency approval / authentication implementation.** The pinned pair is demonstrably wire-compatible for the tested browser-to-Go registration and KE3-verified login, and the Bun and Chromium paths are reproducible. No password or client-secret-state POST was observed. This resolves the basic interoperability uncertainty only. The exact Rust/WASM dependency closure and RUSTSEC-2026-0387 applicability are unresolved; Bytemare remains unaudited; the isolated Go graph's reported advisories have been remediated; browser measurements are one desktop headless sample. The authorized human has not approved either dependency or accepted the unaudited implementation risk. Keep issue #2 open and do not unblock application authentication. Lifecycle/replay/expiry/concurrency, production HTTPS/CSP/browser support, and independent security review remain out of scope for this experiment and required before shipping.
